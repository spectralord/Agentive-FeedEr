# ADR 0024 — On-demand Write-up generation, on the Claude Code subscription

- Status: **accepted** 2026-08-01 (user decision; strong-model design)
- Date: 2026-08-01
- Related: ADR 0017 (the Write-up pass — this ADR resolves all three of its open questions),
  ADR 0015 (execution model / executor seam, **binding**), ADR 0010 (admin manual trigger),
  ADR 0005 (sourced-only), ADR 0003 (null over hallucination),
  design doc §2.2 (Detail's Write-up tab)
- Supersedes: nothing. Amends ADR 0017's "Open questions" section only.

## Context / Problem

ADR 0017 accepted the `reels.writeup` field and the Write-up tab, but deliberately left *how the
field gets filled* proposed. The tab has therefore shipped showing a labelled placeholder for
every Reel — `writeup` is `NULL` for all 16 seeded rows — which was the right interim call
(evaluating the flow needs the tab present) but is not a destination.

Its three open questions all pointed at the same unstated assumption: that generation would be a
**batch pipeline step**, whose only design freedom was *which* Reels to spend money on. Every
proposed answer was a cost-control heuristic — gate on `QUALITY_THRESHOLD`, gate on Top-N/day.

Two facts make that framing wrong for this product:

1. **This is a single-user tool.** `QUALITY_THRESHOLD` and "Top-N/day" are proxies for "content
   someone will probably open". In a product with exactly one reader, the reader opening a Reel
   *is* that signal, available directly and for free. Predicting the interest of one person who
   could instead press a button is strictly worse than the button.
2. **The paid API is not the only way to run inference.** ADR 0015 already built a second
   executor (`claude-code`, Epic 17 T17.1–T17.5/T17.7) that performs structured inference through
   the local `claude` CLI in headless mode, spending **Claude Code subscription quota** and never
   touching `ANTHROPIC_API_KEY`. The cost pressure that motivated gating does not apply to it.

The owner's requirement, stated 2026-08-01: the write-up should be generated by *their Claude
subscription*, not the API, and preferably triggered from the app.

## Decision

1. **Generation is user-triggered, per Reel, from the Write-up tab.** When `writeup IS NULL`, the
   tab renders — alongside the existing labelled placeholder — a **"Generate write-up"** action.
   Pressing it generates the write-up for that one Reel, persists it, and re-renders the tab with
   real prose. No batch pass, no gating heuristic, nothing generated speculatively.

2. **It runs through the existing `claude-code` executor — the subscription, not the API.** The
   route resolves the executor exactly as `pipeline.ts:53` does
   (`getExecutor(resolveExecutionConfig(env()))`) and injects it into the write-up step. No new
   execution machinery, no second inference path, no direct `callStructured`. ADR 0015's mandate
   applies unchanged: injected `Executor`, zod-validated output, unit test with a **mocked**
   caller.

   The money guarantee is **enforced, not merely intended**: `resolveExecutionConfig` throws when
   `APP_PROFILE=local` is combined with `executor=api` (`src/lib/executor/config.ts`), and
   `APP_PROFILE` now defaults to `local`. A misconfiguration fails loudly instead of quietly
   spending credit.

3. **Local-profile-only, by construction — and this is a real limitation, not an oversight.**
   The `claude-code` executor `spawn`s the `claude` binary, so it requires the CLI to be installed
   on the machine hosting the app. That holds locally (verified: `/opt/homebrew/bin/claude`,
   v2.1.212) and **cannot hold on Railway**, where no such binary exists.

   Consequence, stated plainly: under `APP_PROFILE=cloud` this button must be **hidden or
   disabled**, not left to fail at runtime. Since local is currently the only live environment
   (Railway is dormant, see ADR 0006/0015 notes), this costs nothing today — but a future
   reactivation must not silently ship a dead button.

4. **Once generated, cached for good.** `writeup` is a persisted nullable column, so a write-up is
   a one-time cost per Reel and is thereafter served to every subsequent read — and, in any
   multi-user future, to every user. The action is idempotent in effect: a Reel that already has a
   write-up does not offer it again.

5. **Sourced-only, from already-stored content (ADR 0017 decision 3, unchanged).** The write-up
   elaborates on `raw_items.raw_content` — no new fetching. It may use more of that content than
   the short `summary` does, but may not introduce claims the source does not support. This is
   **not** the Deep-Dive (Epic 8), which is agentic and fetches new external pages; reusing that
   term here would collide with a reserved glossary entry (`CONTEXT.en.md`).

6. **Failure is visible and leaves no partial state.** The CLI can fail (not installed, quota
   exhausted, non-zero exit) and zod validation can reject the output. Either way `writeup` stays
   `NULL`, the placeholder remains, and the UI surfaces that the attempt failed rather than
   silently doing nothing. Per ADR 0003 a rejected/unparseable response is **never** written as
   prose, and `summary` is never silently re-shown as a write-up.

## Alternatives

- **Batch pass over every enriched Reel** (ADR 0017's implicit assumption). Rejected: spends quota
  ahead of demand, on a corpus where most items will never be opened by the only reader.
- **Batch, gated on `QUALITY_THRESHOLD` or Top-N/day.** Rejected: popularity/quality proxies for a
  one-person audience, as argued in Context. Also couples write-up behaviour to a threshold tuned
  for a different purpose (feed filtering).
- **A generic task table + typed handlers + a Claude Code schedule polling every ~15 min.**
  Proposed by the owner as a fallback *in case* the app could not invoke `claude` directly. It can
  (decision 2), so this is not needed here — an HTTP request that shells out synchronously is
  simpler than a queue plus a poller. The idea is not discarded, only decoupled: it is an
  architectural question for work that must be asynchronous, parked as **ADR 0025
  (proposed)** with its open questions written down.
- **Keep the placeholder indefinitely.** Rejected: the tab was always meant to hold real content;
  ADR 0017's amendment called the placeholder an interim measure for evaluating flow.

## Consequences

- New executor-backed module (`src/lib/writeup/`) with a prompt, a zod schema, and a unit test
  using a mocked caller — the same shape as `src/lib/verifier/`, `src/lib/skilltagger/`.
- New route to trigger generation for one Reel id, resolving the executor as `pipeline.ts` does.
  It mutates, so it follows the existing POST-and-redirect pattern used by the other mutation
  routes (`/skills/[slug]/progress`, `/saved/[id]/remove`).
- `ReelDetail`'s Write-up tab gains the action in its `writeup === null` branch, plus pending and
  error states. The placeholder copy stays for the not-yet-generated case.
- **Cloud-profile guard:** the action must be hidden/disabled when the resolved executor is `api`
  (see decision 3). A test should pin this so a Railway reactivation cannot ship a dead button.
- ADR 0017's three open questions close; its status becomes fully accepted.
- No new runtime dependencies. No schema migration — `reels.writeup` already exists.
- Epic 18's "still blocked: the Write-up enrichment pass" note is now unblocked in a different
  shape than that note assumed, and should be updated when the work is scheduled.

## Open questions

- **Model choice for the write-up prompt.** ADR 0017 asked whether long-form prose warrants a
  stronger model than enrichment's Haiku default. Under decision 2 the executor resolves the
  model, so this is no longer a cost decision — but the `claude-code` executor does accept an
  optional `model`, so a deliberate choice is still available if write-up quality proves
  model-sensitive. Deferred until there is real output to judge.
- **Regeneration.** Decision 4 makes the action one-shot per Reel. Whether a "regenerate" affordance
  is wanted (e.g. after improving the prompt) is a small, separable UX question, not answered here.
